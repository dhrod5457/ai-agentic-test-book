# 2장. 가장 낮은 테스트 계층에서 잡아라

테스트를 잘 만들고 싶다고 하면 많은 팀이 먼저 테스트 종류부터 떠올린다. Unit Test, Integration Test, Contract Test, E2E Test 같은 이름이 줄줄이 나온다.

하지만 실제 개발에서는 이름보다 먼저 물어야 할 질문이 있다.

> 이 오류를 가장 싸고 빠르게 잡을 수 있는 곳이 어디인가?

이 질문을 기준으로 보면 테스트 전략이 훨씬 단순해진다.

계산식 하나를 검증하는데 브라우저를 띄울 필요는 없다. SQL 문법 오류를 확인하는데 repository 전체를 mock으로 감싸도 안 된다. 로그인부터 결제 완료까지의 전체 흐름을 확인해야 하는데 service method 하나만 호출해서도 부족하다.

좋은 테스트 전략은 많은 종류의 테스트를 쓰는 것이 아니라, 각 오류를 가장 적절한 위치에서 잡는 것이다.

## 가장 싼 곳에서 먼저 잡는다

예를 들어 등록금 계산 로직이 있다고 하자.

학생의 학점 수와 장학금 비율에 따라 최종 금액을 계산한다.

이 로직이 틀렸는지 확인하려면 브라우저를 띄우고 로그인하고 학생을 선택하고 등록금 화면까지 이동할 필요가 없다.

입력값과 기대 결과만 있으면 된다.

이런 경우에는 작은 단위의 테스트가 가장 적절하다.

반대로 SQL을 수정했다고 하자.

쿼리에 컬럼명을 잘못 썼거나 DB 함수가 실제 환경에서 다르게 동작할 수 있다.

이때 repository를 mock으로 바꾸고 service test만 돌리면 테스트는 빠를 수 있다. 하지만 우리가 정말 확인해야 할 SQL은 한 줄도 실행되지 않는다.

이 경우에는 실제 데이터베이스와 연결된 테스트가 필요하다.

즉 테스트 선택 기준은 단순하다.

> 오류가 생길 수 있는 실제 경계를 통과해야 한다.

## 작은 계산은 작은 테스트로

가장 빠르고 단순한 테스트는 작은 함수나 규칙 하나를 직접 검증하는 테스트다.

예를 들어 다음과 같은 규칙이 있다고 하자.

- 10학점 이상 수강하면 장학금 5%
- 15학점 이상 수강하면 장학금 10%
- 휴학생은 장학금 대상 제외

이런 규칙은 입력과 결과가 명확하다.

브라우저도 필요 없고, DB도 필요 없고, 외부 서버도 필요 없다.

이런 테스트는 매우 빠르기 때문에 PR을 올릴 때마다 수백 개, 수천 개를 실행해도 부담이 작다.

이 책에서는 이런 테스트를 가장 낮은 계층의 테스트라고 부른다.

핵심은 이름보다 특성이다.

- 실행이 빠르다.
- 실패 원인을 찾기 쉽다.
- 외부 상태의 영향을 거의 받지 않는다.
- 많은 경우를 값만 바꿔가며 검증할 수 있다.

Agent가 비즈니스 규칙을 수정했다면 가장 먼저 이 계층에서 잡을 수 있는지 확인해야 한다.

## 값 몇 개만 넣어 보는 것으로 충분하지 않을 때

작은 테스트도 잘못 만들면 빈틈이 생긴다.

예를 들어 할인율 계산 테스트가 다음 세 개뿐이라고 하자.

- 100원
- 1000원
- 10000원

전부 정상적인 양수 값이다.

하지만 실제로는 0원, 음수, 최대값 근처, 잘못된 입력 같은 경우가 더 중요할 수 있다.

이럴 때는 특정 예시 몇 개만 고르는 대신 입력 범위를 넓게 확인하는 방법을 사용할 수 있다.

예를 들어 다음 성질을 검증할 수 있다.

> 할인 후 금액은 원래 금액보다 커지면 안 된다.

> 할인율은 0%에서 100% 사이여야 한다.

> 같은 입력에는 같은 결과가 나와야 한다.

이처럼 특정 값 하나가 아니라 항상 지켜져야 하는 성질을 기준으로 여러 입력을 자동으로 만들어 검증하는 방법을 속성 기반 테스트(property-based testing)라고 한다.

Agent가 몇 개의 예시만 만들고 끝내는 것을 막는 데 특히 유용하다.

## 실제 DB를 통과해야 하는 오류

이제 repository 쿼리를 수정했다고 하자.

다음과 같은 문제는 작은 단위 테스트만으로는 잡기 어렵다.

- SQL 문법 오류
- 잘못된 컬럼명
- 실제 DB의 정렬 방식
- transaction 경계
- unique constraint
- timestamp 처리
- DB별 함수 차이

이런 문제는 실제 데이터베이스를 통과해야 드러난다.

그래서 Java/Spring에서는 Testcontainers 같은 도구로 실제 DB 컨테이너를 띄워 테스트할 수 있다.

도구 이름이 중요한 것은 아니다.

중요한 기준은 다음이다.

> 검증하려는 위험이 실제 DB 동작에 있다면 테스트도 실제 DB를 지나가야 한다.

반대로 계산식 하나를 확인하는데 매번 DB를 띄울 필요는 없다.

테스트 계층은 결국 비용과 현실성 사이의 선택이다.

## 서비스 사이의 약속을 확인하는 테스트

마이크로서비스나 외부 API를 사용하는 시스템에서는 또 다른 문제가 생긴다.

서비스 A는 다음 JSON을 보낸다고 가정한다.

```text
{
  "studentId": 1001,
  "status": "ACTIVE"
}
```

그런데 서비스 B가 필드명을 `student_id`로 기대한다면 서로의 코드가 각각 잘 동작해도 연결 순간에 실패한다.

이런 문제는 두 서비스를 처음부터 끝까지 모두 띄우지 않고도 확인할 수 있다.

서로 주고받기로 한 요청과 응답의 형태를 테스트하는 것이다.

이런 테스트를 계약 테스트(contract testing)라고 한다.

계약 테스트의 장점은 전체 E2E보다 훨씬 빠르면서도 서비스 경계 오류를 잘 잡을 수 있다는 점이다.

즉 E2E에서 잡을 수 있는 일부 문제를 더 싼 계층으로 내려올 수 있다.

## E2E는 정말 필요한 흐름만 남긴다

이제 사용자 관점에서 전체 흐름이 맞는지 확인해야 할 때가 있다.

예를 들어 다음 흐름은 여러 시스템이 함께 움직인다.

```text
로그인
  ↓
수강신청
  ↓
정원 확인
  ↓
DB 저장
  ↓
신청 결과 화면
```

이런 경우에는 브라우저, 인증, API, 서버, DB가 실제로 이어지는지 확인할 필요가 있다.

이때 E2E 테스트가 의미가 있다.

하지만 여기서 흔한 실수가 생긴다.

새 기능이 하나 생길 때마다 E2E 테스트를 하나씩 추가하는 것이다.

처음에는 괜찮다. 시간이 지나면 다음 문제가 쌓인다.

- 로그인 반복
- 브라우저 기동 비용
- 데이터 준비 시간
- 네트워크 대기
- sleep 증가
- 공유 상태 충돌
- flaky 증가

결국 테스트는 많아지지만 피드백은 느려진다.

그래서 E2E는 많이 만드는 것이 아니라 중요한 사용자 흐름만 남겨야 한다.

## 같은 오류를 여러 계층에서 확인할 필요는 없다

예를 들어 할인 계산 오류를 이미 빠른 단위 테스트에서 충분히 잡고 있다고 하자.

그런데 같은 할인 계산식의 모든 경우를 E2E에서도 반복해서 확인한다면 실행비용만 늘어난다.

E2E에서는 다음 정도만 확인하면 충분할 수 있다.

> 할인 대상 사용자가 주문을 완료했을 때 실제 최종 금액이 화면에 반영되는가?

세부 계산 경계값은 아래 계층에서 검증하고, E2E는 시스템이 이어지는지만 확인한다.

이 원칙을 테스트 피라미드라는 그림으로 설명하기도 하지만, 그림 자체보다 중요한 판단 기준은 이렇다.

> 같은 오류를 잡을 수 있다면 더 빠르고 단순한 테스트를 우선한다.

## Agent가 테스트를 고를 때의 순서

Agent에게 새 기능을 구현하게 할 때 단순히 “테스트도 추가해”라고 하면 가장 익숙한 방식으로 테스트를 만들 수 있다.

대신 다음 질문을 순서대로 답하게 하는 편이 낫다.

첫째, 이 변경에서 실제로 깨질 수 있는 것은 무엇인가?

둘째, 그 오류를 가장 낮은 계층에서 잡을 수 있는가?

셋째, 실제 DB나 외부 서비스 경계를 꼭 통과해야 하는가?

넷째, 전체 사용자 흐름을 검증해야 하는가?

이 순서로 보면 테스트 선택이 자연스러워진다.

예를 들어:

```text
계산식 변경
→ Unit / Property

SQL 변경
→ DB Integration

외부 API 응답 구조 변경
→ Contract

인증부터 업무 완료까지 핵심 흐름
→ E2E
```

## Mock은 속도를 높이지만 현실을 지울 수도 있다

테스트를 빠르게 만들기 위해 mock을 사용하는 경우가 많다.

mock은 외부 의존성을 가짜 객체로 바꿔 테스트 대상을 격리하는 방법이다.

이 자체가 잘못된 것은 아니다.

문제는 실제로 확인해야 할 경계까지 전부 mock으로 바꿀 때다.

예를 들어 SQL을 수정했는데 repository를 mock하면 테스트는 빠르게 통과할 수 있다.

하지만 SQL 문법이 틀려도 아무도 모른다.

그래서 Agent가 mock을 만들 때는 다음 세 가지를 설명하게 할 수 있다.

1. 무엇을 격리하려는가?
2. 왜 실제 의존성을 사용하지 않는가?
3. 실제 연결은 다른 테스트에서 어디서 검증되는가?

이 세 질문에 답할 수 없다면 mock이 너무 넓을 가능성이 있다.

## 빠른 테스트와 현실적인 테스트는 경쟁 관계가 아니다

작은 테스트는 빠르지만 실제 연결을 덜 본다.

큰 테스트는 현실적이지만 느리고 실패 원인을 찾기 어렵다.

둘 중 하나만 선택하는 것이 아니다.

각자 잘하는 일을 맡기면 된다.

```text
Unit
→ 작은 규칙

Property
→ 넓은 입력 범위

Integration
→ DB, transaction, 실제 dependency

Contract
→ 서비스 사이의 약속

E2E
→ 핵심 사용자 흐름
```

이렇게 역할을 나누면 E2E 개수를 줄이면서도 검증 범위는 오히려 더 분명해진다.

## 이 장에서 가져갈 세 가지 규칙

첫째, 같은 오류를 잡을 수 있다면 가장 빠르고 단순한 테스트 계층을 선택한다.

둘째, 실제 DB나 서비스 경계가 위험한 부분이라면 mock으로 숨기지 않는다.

셋째, E2E는 모든 기능의 상세 규칙을 반복 검증하는 곳이 아니라 핵심 흐름이 실제로 연결되는지 확인하는 곳이다.

다음 장에서는 여기서 한 단계 더 들어간다.

> 테스트 파일은 있는데 실제로는 아무것도 검증하지 않는다면 어떻게 알아낼까?

Agent가 만들기 쉬운 쓰레기 테스트, 억지로 성공시키는 테스트, 의미 없는 assertion을 구체적으로 살펴본다.
