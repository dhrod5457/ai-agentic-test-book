# Test Maintenance and Technical Debt\n\n기준일: 2026-10-05\n\n이 문서는 AI coding agent가 테스트를 계속 추가하면서 만드는 유지보수 비용과 테스트 기술부채를 연구한다.\n\n## 1. 왜 테스트 코드도 기술부채가 되는가\n\n2026 TOSEM의 Self-Admitted Technical Debt 연구는 테스트 코드의 debt를 production code와 별개로 분석할 필요가 있음을 보여준다.\n\n테스트는 product code를 검증하지만 그 자체도 변경되고 이해되고 유지되어야 하는 소프트웨어다.\n\nAgent가 테스트를 무조건 늘리면 다음 비용이 누적된다.\n- 중복 setup\n- 중복 assertion\n- fixture 폭증\n- brittle internal interaction 검증\n- 과도한 mock\n- test smell\n- execution time 증가\n- flaky surface 증가\n\n## 2. 2026 LLM-Generated Test Smell Study\n\n출처:\n- "On the Diffusion of Test Smells in LLM-Generated Unit Tests", ACM TOSEM, 2026\n\n규모:\n- LLM generated class-level suites: 20,505\n- method-level cases: 972\n- EvoSuite tests: 14,469\n- human-written tests: 779,585\n- Java OSS projects: 34,635\n- detectors: TsDetect + JNose\n\n주요 관찰:\n- LLM-generated Java tests에서도 Assertion Roulette와 Magic Number Test가 반복적으로 나타남\n- smell 분포는 prompting, context length, model scale의 영향을 받음\n- 일부 패턴은 human-written tests와 유사\n- EvoSuite는 또 다른 generator-specific flaw를 보임\n\n### 책에서의 의미\n\nLLM이 테스트를 생성한다는 이유로 test smell 문제가 사라지지 않는다.\n오히려 사람 코드의 흔한 나쁜 패턴을 모방하거나 generator 특유의 나쁜 패턴을 새로 만들 수 있다.\n\n## 3. 2026 Test Smell Mapping\n\n2026 Journal of Systems and Software systematic mapping:\n- 50 test smells\n- 94 refactorings\n- 31 tools\n- Java가 가장 많이 연구된 언어\n- 자주 인용되는 smell: Assertion Roulette, Eager Test\n- critical smell: Sleepy Test, Ignored Tests, Resource Optimism, Mystery Guest\n\n### Agent 규칙으로 변환\n\nAgent가 만든 테스트도 production code와 마찬가지로 정적 품질 검사를 통과해야 한다.\n\n## 4. 중복 테스트\n\n중복은 단순히 동일한 코드 복사를 의미하지 않는다.\n\n다음이 같으면 semantic duplication 가능성이 있다.\n- 같은 failure mode\n- 같은 input partition\n- 같은 system boundary\n- 같은 assertion target\n- 같은 regression cause\n\nAgent는 새 테스트를 추가하기 전에 기존 suite에서 같은 목적의 테스트를 검색한다.\n\n중복 테스트가 문제가 되는 이유:\n- 실행시간 증가\n- 요구사항 변경 시 수정 지점 증가\n- 같은 brittle assumption 확산\n- 실패 로그 중복\n- CI noise 증가\n\n### 규칙 후보\n\n> 테스트 개수보다 고유한 failure mode 수를 늘린다.\n\n## 5. Brittle Test\n\nbrittle test는 외부 observable behavior보다 내부 구현 세부에 지나치게 결합된 테스트다.\n\n예:\n- private/internal 호출 순서 검증\n- mock invocation count를 이유 없이 고정\n- 내부 collection 구현 타입 검증\n- SQL 내부 조각까지 snapshot\n- DOM 구조의 불필요한 세부 selector\n\n문제:\n기능은 그대로인데 refactoring만으로 테스트가 깨진다.\n\nAgent는 assertion을 다음 순서로 선호한다.\n1. business outcome\n2. externally observable state\n3. contract\n4. 꼭 필요한 interaction\n5. internal implementation detail은 최소화\n\n## 6. 과도한 Mock\n\nmock 자체는 문제가 아니다.\n\n문제는 실제로 검증해야 할 경계를 모두 mock 처리하는 것이다.\n\n예:\nSQL 변경 -> repository mock -> service test green\n\n이 테스트는 SQL correctness를 검증하지 않는다.\n\n다음 경계는 실제 구현 테스트가 필요한 경우가 많다.\n- DB query\n- serialization\n- transaction\n- message schema\n- security filter\n- HTTP contract\n\nAgent는 mock을 추가할 때 다음을 설명해야 한다.\n- 무엇을 격리하려는가\n- 왜 실제 dependency를 사용하면 안 되는가\n- 실제 integration은 어디서 검증되는가\n\n## 7. Fixture Explosion\n\nfixture가 점점 커지면 테스트 한 개의 목적을 이해하기 어려워진다.\n\n징후:\n- 모든 필드가 들어간 거대한 builder\n- unrelated entity 수십 개 생성\n- BeforeEach setup이 테스트 본문보다 김\n- 하나의 fixture 변경으로 수십 테스트 실패\n\n대안:\n- 최소 fixture\n- domain factory\n- scenario-specific builder\n- irrelevant default 숨김\n- shared global mutable fixture 금지\n\n원칙:\n\n> 테스트 준비 데이터는 테스트가 검증하는 조건만 드러내야 한다.\n\n## 8. Assertion Roulette\n\n한 테스트에 많은 assertion이 있지만 실패했을 때 어떤 business condition이 깨졌는지 알기 어려운 패턴.\n\n개선:\n- 의미 있는 assertion grouping\n- descriptive assertion message\n- 하나의 scenario에서 관련 결과만 묶기\n- 서로 다른 failure mode는 별도 test로 분리\n\n단, 무조건 assertion 하나당 test 하나를 만들지는 않는다.\n\n## 9. Magic Number Test\n\nexpected value가 왜 그 숫자인지 설명되지 않는 테스트.\n\n예:\nassertThat(result).isEqualTo(137)\n\n더 좋은 형태:\n- domain constant\n- 의미 있는 변수명\n- 계산 근거가 보이는 expected setup\n\n단, production method를 expected 계산에 재사용해서는 안 된다.\n\n## 10. Ignored / Disabled Test Debt\n\n@Disabled/@Ignore는 실패를 없애는 것이 아니라 검증을 제거한다.\n\nAgent가 disable을 추가하는 경우 기본적으로 실패 처리한다.\n\n예외:\n- 명시적인 quarantine workflow\n- owner\n- reason\n- expiry\n- issue link\n\n가 있는 경우에만 임시 허용을 검토한다.\n\n## 11. 자동 Refactoring\n\n2026 ENASE 연구는 20개 이상의 test smell을 분석하고, 그중 10개 smell을 자동 탐지·refactor하는 도구 접근을 평가했다.\n\n시사점:\nAgent는 테스트를 새로 생성하는 역할뿐 아니라 기존 test smell을 정리하는 역할도 가져야 한다.\n\n그러나 자동 refactoring 후에도 behavior preservation을 별도 검증해야 한다.\n\n## 12. 테스트 추가 전 Decision\n\nAgent는 새 테스트 추가 전에 다음 순서를 따른다.\n\n1. 기존 테스트가 같은 failure mode를 검증하는가?\n2. 기존 테스트를 보강하면 되는가?\n3. parameterized/property test로 합칠 수 있는가?\n4. fixture를 재사용할 수 있는가?\n5. 새 테스트가 새로운 unique risk를 검증하는가?\n\n모두 검토한 후 새 테스트를 추가한다.\n\n## 13. 유지보수 Gate 후보\n\n정적:\n- assertion count / assertion smell\n- magic literal\n- sleep\n- disabled\n- empty test\n- duplicated setup\n- oversized fixture\n- excessive mocking\n\n동적:\n- test duration\n- flakiness\n- mutation score\n- duplicated failure coverage\n\nreview:\n- why this test exists\n- what unique failure it catches\n- why this layer is appropriate\n\n## 14. 핵심 원칙\n\n> 테스트는 많을수록 좋은 것이 아니라, 서로 다른 실패를 싸게 잡을수록 좋다.\n\n> Agent가 테스트를 추가할 수 있다면 테스트를 삭제·통합·리팩터링해야 할 때도 판단할 수 있어야 한다.\n\n> 테스트 코드의 유지보수성도 제품 코드와 같은 수준으로 관리해야 한다.
